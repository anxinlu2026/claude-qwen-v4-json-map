# 規劃：方塊骨架 + 方塊測試 + RTL 對應表（v4 流程修正）

來源：使用者 2026-10-18 對流程的更正。本文件是規劃，尚未實作；實作前先與使用者確認「待決定」各項。

## 1. 與先前流程的差異
| | 先前 | 修正後 |
|---|---|---|
| 對齊對象 | 逐方塊填「端口表」，之後才談功能 | 逐方塊填「RTL 對應表」，端口、功能、控制一起處理 |
| 功能比對 | 另一階段（c3） | 對齊時就用 **方塊層級 testbench harness** 驗證 RTL |
| 控制 | 暫不分析 | HDL 對齊時**同時評估控制的對錯** |
| 順序 | 方塊任意 | 依架構給的資料路徑連結順序，**由輸入往輸出** |
| 交付 | 端口 JSON | 對應表：RTL 範圍、上下游端口、驗證結果、信心度、難度、控制評估 |

## 2. 角色與交付

### 架構提供（只依規格，不看 RTL）
1. **資料路徑 JSON 骨架**：依規格功能切成子方塊，每個子方塊一份 JSON（埠、功能、Python 實作）；加上 top JSON（子方塊的連接關係與參數）。**top + 子方塊 JSON 串起來必須通過 testbench harness**（現有 `harness_check.py` 的做法）。
2. **方塊層級 testbench harness**：把 top testbench 的激勵送進模型串，傾印每個子方塊的輸入與輸出，作為該方塊的 stimulus 與 expected。expected 來自模型（模型的端到端結果已由 top testbench 的期望值驗證），不來自 RTL。
3. **連結順序**：資料路徑方塊由輸入到輸出的順序（拓撲序）。
4. **預期活動表**（隨 harness 附上）：每個方塊在模型時程的哪幾個步驟有效，供 HDL 評估控制時當依據。

### HDL（Qwen）提供：每個方塊一份「RTL 對應表」
依連結順序、由輸入往輸出，逐方塊填：
- **對應的 RTL**：檔案與行號範圍，標明類型（always_ff / always_comb / assign / instance）。
- **上下游端口訊號**：方塊每個埠對應的 RTL 訊號、方向、寬度、類型、有效條件、clock/邊緣、延遲（沿用現有端口 JSON 欄位）。
- **驗證結果**：用方塊 harness 跑 RTL 的原始輸出（吻合幾列、不符幾列、哪些位元組）。
- **信心度**（高/中/低）與**難度**（易/中/難），各附一句原因。
- **控制評估**：該方塊的有效條件與時序是否與預期活動表一致（一致／可疑／無法判斷），附證據（探測原文）。
- **unknown**：看不出來的欄位，不猜。

HDL 只記錄事實與評估，**不修改 RTL、不下根因結論**；差異的意義由架構判斷。

### 架構之後
讀所有對應表：判斷信心度低、難度高、驗證不符、控制可疑的方塊；改模型（只依規格）或把疑問寫成假設並出 PROVE 工單，再進修改與確認。

### orchestrator
原樣轉發架構的工單、計時、形式檢查（JSON 合法、無 TODO、欄位齊全）、看板與決策日誌；不寫工單、不裁決技術問題。

## 3. 方塊 harness 的兩種檢查（建議都做）
1. **功能檢查**：用 RTL 自己探測到的方塊輸入，餵進方塊的 Python 函式，與 RTL 的方塊輸出比對（現有 `rtl blockcheck`）。上游有錯也不會遮住下游。
2. **輸入檢查**：RTL 實際送進方塊的輸入，是否等於 harness 的期望輸入。若不等，表示上游沒把正確的資料送來，這是「控制或上游」的線索，不是這個方塊的功能問題。
兩者合起來，才能分清「這個方塊自己錯」與「上游或控制讓它拿到錯的輸入」。

## 4. 實作項目與驗收
| 階段 | 項目 | 驗收 |
|---|---|---|
| P1 | 子方塊 JSON 骨架 + top JSON + 連結順序（沿用 `arch/model.json`，補成每方塊獨立檔與 top） | top + 子方塊串起來通過 harness（ALL PASS） |
| P2 | 方塊 harness 產生器：由 top testbench 激勵經模型傾印每方塊的輸入輸出與預期活動表 | 逐方塊 stimulus/expected 檔；串起來端到端等於 testbench 期望值 |
| P3 | 方塊 harness 執行器：讀 RTL 對應表，在容器內用 `rtl probe`/`blockcheck` 比對，輸出每方塊結果 | 在**參考解 RTL**（已修好的）上，所有方塊全吻合；在原始 RTL 上，已知有問題的方塊顯示不符 |
| P4 | 對應表 JSON 骨架 + 格式檢查（沿用 `fill_port.py` 的做法擴充欄位） | 骨架合法；填值有取值檢查；腳本列出缺漏 |
| P5 | 架構寫對應表工單模板（一方塊一張，依連結順序）；Qwen 用對話測試理解後，在新 cell 執行頭兩個方塊 | 兩個方塊的對應表齊全，harness 結果可重現，耗時記錄 |
| P6 | 15 個方塊全做；架構讀表、判斷、出 PROVE 工單 | 對應表齊全；每個差異有架構的判斷紀錄 |

## 5. 風險
- Qwen 找對應 RTL 的準確度（讀碼為主）。以 harness 的輸入檢查、參考解上的驗證來抓。
- 沒有參考解時，無法確認對應表本身正確：靠「上游吻合的方塊證明對應表用法對」，不符的方塊才需區分「RTL 錯」與「對應錯」。
- 控制評估的依據是預期活動表；規格沒定義的行為（例如忙碌中收到 start），標「無法判斷」，由架構決定。
- 一張工單的 15 分鐘限制：一方塊一張，必要時兩三個小方塊合一張。
