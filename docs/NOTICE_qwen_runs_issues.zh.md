## I. thinking 設定問題：用 Claude Code 當介面帶來的差異與解法

**背景**：先前的 Qwen 流程（walk5、委派實驗）用 Qwen Code，啟動參數明確是 `--reasoning-effort none`（thinking 關閉），這是有意的設定（thinking 關閉的 Qwen 在答案文字裡推理）。改用 Claude Code 當介面後，**這個設定沒有被帶過來**，而且在這個介面下沒有簡單的開關。

**問題**：Claude Code 不會對 Ollama 送出「關閉 thinking」的參數；Ollama 對標示有 `thinking` 能力的模型，預設是開。結果 Qwen 每一步都先思考。

**實測（單一問題「1+1」，直接打 Ollama 的 `/v1/messages`；耗時因同時有其他工作搶模型而偏大，只看相對關係）**

| 請求寫法 | 回應區塊 | thinking 字元 | 輸出 token |
|---|---|---|---|
| 預設（不帶任何 thinking 參數）| thinking＋text | 30 | 23 |
| `thinking: {type: disabled}` | **只有 text** | **0** | **1** |
| `thinking: {type: enabled, budget_tokens: 1024}` | thinking＋text | 38 | 32 |
| Ollama 原生欄位 `think: false` | thinking＋text | 30 | 24 |

| Claude Code 的做法（`echo hello` 小任務）| thinking 區塊 | thinking 字元 | 耗時 |
|---|---|---|---|
| 預設 | 有 | — | — |
| 環境變數 `MAX_THINKING_TOKENS=0` | **仍有 2 個** | 1453 | 331 秒（當時有其他工作搶模型）|
| 經本機代理（加 `thinking: disabled`）| **0** | 0 | 28 秒 |

**結論**：只有請求帶 `thinking: {type: disabled}` 才真正關閉；`MAX_THINKING_TOKENS=0` 與 Ollama 的 `think:false` 在這個介面與端點下都無效。Modelfile 也無法關閉（這個模型用 Ollama 內建的轉譯器，thinking 由 API 參數控制）。

**解法**：在 Claude Code 與 Ollama 之間放一個本機代理 `flow/ollama_proxy.py --no-think`（埠 11435），替每個 `/v1/messages` 請求加上 `thinking: {type: disabled}`，其餘原樣轉送（含串流）。驅動用 `--base-url http://127.0.0.1:11435` 指向它。

**驗證與實際效果**
- 實際運行的對話記錄：v6q（沒有代理，thinking 開）停止前，主 session 有 **30 個 thinking 區塊、約 9 萬字元**，1 小時 21 分只寫出 1 份對應表；v6n 與 v6m（有代理）**thinking 區塊 0**（v6m 四個以上的 session、245 個工具呼叫，全程 0）。
- 速度：開 thinking 時約每 2 分鐘一個工具呼叫；關閉後約每 10 到 20 秒一個，對應表約每 10 到 15 分鐘一份。
- 確認方法：不要看 `usage` 裡的 `thinking_tokens`（在這個介面下永遠是 0，不準）；要數對話記錄（`cc_cfg/projects/*/*.jsonl`）裡 `type = thinking` 的區塊數與字元數。

**限制與風險**
1. 代理是額外的一個元件，要記得先啟動；沒啟動時驅動會失敗或（若指到 11434）退回 thinking 開。**建議驅動啟動時檢查代理存活，並在每輪結束時數 thinking 區塊，非 0 就警示。**
2. 我只能從結果（有沒有 thinking 區塊）判斷，看不到 Claude Code 實際送給 Ollama 的內容；代理直接測試（1 token 輸出）是最直接的證據。
3. **未驗證**：其他取樣設定是否也因介面而不同。Ollama 模型自帶的參數是溫度 0.6、`top_p` 0.95、`top_k` 20、`presence_penalty` 0.5、`frequency_penalty` 0.5、`repeat_penalty` 1.1、`num_ctx` 262144；先前 Qwen Code 流程明確傳了溫度 0.6 與三個懲罰值。Claude Code 的請求是否覆寫了這些，我沒有驗證；比較報告要註明「取樣參數可能不同」。
4. thinking 關閉與先前的 Qwen 流程一致，但與第一次運行（Codex／Claude session）的設定未知，不能直接比較速度。

**建議（通用）**
- 換介面或換 agent 時，把「模型設定清單」（thinking、溫度、懲罰、上下文長度、逾時）列出來逐項核對；設定要明確記錄，不依賴預設。
- 把「關 thinking」做成驅動的預設選項（含代理的啟動與存活檢查）。
- 設定的驗證要看原始記錄（對話記錄中的區塊），不看摘要欄位。

## J. Qwen 處理 blk0 到 blk3 的流程分析與改善空間（技能與工具）

資料來源：v6m 的所有對話記錄（工具呼叫、時間戳記、內容大小）。注意：記錄含我的 session 重開 bug 造成的重讀（見 A1），所以「讀檔」的次數偏高；時間線已扣除 session 暫停的約 5 小時。「輸出 token」是用字元數估的（約 0.6 token 每字元），不是實測。

### J1. 實測剖面
| 項目 | 數據 |
|---|---|
| 工具呼叫類別（全部 session）| 讀架構檔 97（30 個不同檔案，被重讀約 3 倍）、`rtl show` 18、`rtl probe` 16、寫或改 hdl 檔 18、`block_harness` 6、`validate_json` **1**、被權限拒絕 49（絕大多數是 B1 的 `ls` 迴圈）|
| 每一步的模型延遲（中位數）| `Bash` 68 秒、`Read` 58 秒、**`Write` 310 秒（約 5 分鐘）**、`Edit` 160 秒 |
| 寫 hdl 檔 | 18 次，單次 383 到 18408 字元（多數 8 千到 1.8 萬），合計約 12.8 萬字元，估計約 7.7 萬輸出 token（以每秒約 32 token 算約 40 分鐘純生成）；同一個檔案重寫：blk1 6 次、blk3 7 次、blk2 3 次、blk0 2 次 |
| 第一份方塊的完成時間 | blk0 約 39 分鐘（含讀檔與探測）、blk1 約 15 分鐘；接續後 blk2 約 31 分鐘、blk3 約 13 分鐘 |
| 回頭修改的時間 | 兩次提示後重寫 blk0 到 blk3，共 8 次寫入，約 **88 分鐘**（比第一次寫的時間還多）|
| 自己跑驗證 | `validate_json` 只跑 1 次（18 次寫入裡），`block_harness` 6 次；錯誤多半是我的提示與工具規則逼出來之後才被改 |
| 探測的錯誤 | 2 次（zsh 對未加引號的 `x[0]` 做路徑展開，`no matches found`），它自己發現並加引號 |

### J2. 觀察
1. **主要成本是「整份重寫 JSON」**：一次 `Write` 約 5 分鐘，18 次；而且欄位裡有長篇文字（理由、證據、解釋），重寫時又改動其他欄位，錯誤跟著重新出現（blk3 重寫 7 次）。
2. **回饋太晚**：格式問題要等我（orchestrator）提示、或它自己想到才去跑 `validate_json`；寫了 18 次，只主動驗證 1 次。第一次檢查的錯誤（`signal` 是說明文字、`storage` 超出允許值、信心度與證據不符）本來可以在寫入的當下就被擋下。
3. **一次讀完全部 30 個架構檔案**：每個檔案一個模型步驟（約 1 分鐘），而且每次接續都重讀；實際上每個方塊只需要它自己的模型、harness、骨架與少數 RTL 片段。
4. **找訊號靠多次 `rtl signals` 與 `rtl show`**：沒有「這個埠最可能對應哪些 RTL 訊號」的候選清單，blk2、blk3 的訊號找了很久；找不到就退到 `none` 或說明文字。
5. **harness 回報 0 列時沒有診斷**：Qwen 看到「0 列」不知道是 `active_when` 寫法解析失敗、條件永遠不成立，還是訊號不對。它的 `active_when` 用了 Verilog 的 `11'd0` 字面值，不確定 `rtl blockcheck --when` 是否能解析。
6. **模型的做法本身是謹慎的**：引用行號與原文正確、不確定處用 `unknown`、能自己修正工具的錯誤訊息；弱點在「看到證據不下結論」與「信心度失準」（C1、C2）。

### J3. 改善建議（通用原則；先列技能，再列工具）
| ID | 類別 | 建議 | 預期效果 | 優先 |
|---|---|---|---|---|
| J-1 | 技能 | `unit-alignment` 加「先寫最小可用版本」：第一次只填必要欄位且每個文字欄位限一行（理由與證據各不超過 200 字元），跑工具、通過後再補充；一次只處理一個方塊，只讀該方塊的檔案 | 縮短每次寫入的生成時間，降低重寫次數 | 高 |
| J-2 | 技能 | 加「狀態與信心度要有工具證據」：功能檢查 0 列時，信心度 low、狀態 open，除非有替代證據；看到矛盾的證據要下結論或明確列為疑問，不留在「要再確認」 | 減少 C1、C2 類問題 | 中 |
| J-3 | 工具 | **寫入當下自動驗證**：用 Claude Code 的 hook（`PostToolUse`，對 `exchange/hdl-*.json` 的 `Write`／`Edit`）跑 `validate_json`，把錯誤直接回給模型 | 格式與一致性問題當下就被擋，預期可省掉大部分回頭修的時間（本次約 88 分鐘） | 高 |

| J-6 | 工具 | **harness 的 0 列診斷**：`block_harness` 在 0 列時印出原因：`--when` 解析錯誤、條件在取樣窗內從未為真（附各訊號在窗內的值範圍）、或訊號不存在；對 Verilog 字面值（`11'd0`）給出轉成十進位的建議或自動轉換 | 模型知道怎麼修，不退到 `none` | 中 |
| J-7 | 工具 | **候選訊號建議**：`suggest_signals BLK` 用埠名、寬度、上下游連接、`rtl_structure.json` 的暫存器與依賴，列出最可能的 RTL 訊號 | 減少 `rtl signals` 的反覆呼叫 | 中 |
| J-8 | 工具 | 包裝腳本讓 `rtl` 對含 `[ ]` 的參數不受 zsh 展開影響（例如在 `rtl` 指令前自動 `noglob`，或在 README 明確規定加引號）| 去掉 2 類小錯誤 | 低 |
| J-9 | 驅動 | 偵測到「同一個工具呼叫連續 3 次」或「被拒絕 3 次」時自動中斷該輪並送出程序性提示（附允許的替代工具）| 避免 B1 的 30 分鐘迴圈 | 高 |
| J-10 | 驅動 | 輪次以「進度」管理（有新檔案或新工具呼叫就延長），並每輪開始時顯示「新 session 或接續」| 避免 A1 | 高 |

### J4. 建議的做法順序
1. 先做 **J-3（hook 自動驗證）**與 **J-4（填欄位工具）**：直接針對最大的兩個成本（整份重寫、回饋太晚），而且只需要在驅動與工具端改，不改模型與流程。
2. 接著 **J-5（工作包）**與 **J-9／J-10（驅動）**。
3. 技能 **J-1、J-2** 隨前面的工具一起更新（技能文字要通用，不寫這次的特例）。
4. 改完後用同一個 Qwen 設定重跑 blk0 到 blk3，比較：每個方塊的耗時、重寫次數、驗證次數、格式問題數。
